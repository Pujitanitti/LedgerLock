RESOLVED only when an actual fix has been implemented and verified — not
when it's merely been discussed or judged acceptable for now. This
document is updated every phase, not just when a new risk appears.

## Resolution criteria (Phases 1-5)

- **R-001**: **PARTIALLY MITIGATED, still OPEN**. Rate limiting is now implemented (see fix note above) — the remaining closure requirement is unchanged: platform-admin auth or an invitation/approval flow, actually implemented and tested. Deferred to a dedicated hardening phase — not to be closed by inventing infrastructure ahead of actual need.
- **R-002**: **RESOLVED** — see the fix note in the table above. Verified at the unit level: `RoleAssignmentsService` now passes `tenantId` through to all four join-table methods (tested directly), and `PrismaRbacRepository`'s guarded SQL is reviewable/reasoned about, though its actual execution against real PostgreSQL remains ENVIRONMENT-BLOCKED like every other Prisma-touching query in this project (see R-004/R-005/R-007/R-009) — the fix closes the *design* gap; real-DB verification of the guard SQL itself is still pending an unrestricted environment.
- **R-003**: **RESOLVED** — see ADR-006's "Update (R-003 fix)" section and the fix note in the table above. Fully unit-tested (a key hashed under the old pepper still authenticates when `API_KEY_HMAC_PEPPER_PREVIOUS` is set; fails once it's removed; new keys never use the previous pepper) — this is pure crypto logic with no database/Redis dependency, so unlike most other findings in this register, R-003's fix is verified, not ENVIRONMENT-BLOCKED.
- **R-004 / R-005**: closed once `npm run prisma:generate` succeeds in an unrestricted environment and the CTE has been run against real seeded role hierarchies, with an integration test asserting its output matches `resolveEffectiveRoleIds` for the same graph.
- **R-006**: closed by extending `getEffectivePermissionActions` (or a sibling query) to also return the full set of effective (inheritance-expanded) role IDs, then using that instead of the direct-only role list when building `SubjectAttributes.roles`. Deferred rather than built speculatively in Phase 5 to avoid adding a query to the authorization hot path without a concrete policy author asking for role-inheritance-aware conditions yet.
- **R-007**: closed once `npm run prisma:generate` succeeds and `listCandidateVersionsForCheck` has been run against real seeded policies with multiple versions, confirming `DISTINCT ON` actually returns only the highest-version row per policy.

## Resolution criteria (Phase 6)

- **R-008**: closed by explicitly choosing and wiring a scheduling mechanism for `processBatch()` (a cron dependency, a queue consumer, or an external trigger), with sign-off on the dependency added — deliberately not chosen unilaterally in Phase 6 per "no dependencies without necessity."
- **R-009**: closed once `npm run prisma:generate` succeeds in an unrestricted environment and a real Redis + PostgreSQL instance is available to run the cache/audit/version-bump code paths for real, with integration tests confirming: a cache hit actually skips RBAC/ABAC recomputation, a version bump actually changes the next request's cache key, and an outbox row actually reaches `AuditLog`.
- **R-010**: closed (or explicitly re-accepted) once real traffic/benchmark data shows the actual cache hit-rate impact, at which point the "hash attributes only when a policy reads them" alternative considered in ADR-012 can be revisited with real numbers instead of a priori reasoning.
